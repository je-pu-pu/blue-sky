### プロジェクト簡素化計画：完全な ECS 移行

この計画は、従来の `GameObject` 継承階層と Entity Component System (ECS) を組み合わせた現在のハイブリッドアーキテクチャから、純粋な ECS モデルへのプロジェクト移行手順を概説します。このリファクタリングは、重複する懸念事項と密結合に起因する現在の複雑さに対処することを目的としています。これは大規模なリファクタリング作業であり、各段階で継続的な検証を行いながら段階的に実行する必要があります。

#### **フェーズ 1: 基盤の確立と準備**

1.  **コア ECS の見直しと強化:**
    *   `core/ecs` ディレクトリ内のコア ECS コンポーネント（`EntityManager`、`Entity`、`Component`、`BaseSystem`、`System`）が堅牢で、十分にテストされており、プロジェクトの要件を満たしていることを確認します。
    *   コンポーネントのストレージとシステムのディスパッチメカニズムが効率的で、パフォーマンスが高いことを検証します。

2.  **すべての `GameObject` サブクラスとその責務の特定:**
    *   `GameObject` を継承するすべてのクラス（例: `Player`、`Robot`、`Camera`、`ActiveObject`、`StaticObject` など）の包括的なリストを作成します。
    *   特定された各サブクラスについて、その固有のデータメンバー、メソッド、および責務を詳細に文書化します。この詳細な分析は、新しいコンポーネントとシステムを設計する上で非常に重要になります。

3.  **コアコンポーネントの作成（未存在の場合）:**
    *   **`TransformComponent`** (既存): すべての位置、回転、スケールのニーズに十分対応できることを確認します。
    *   **`PhysicsComponent`**: `btRigidBody` とすべての物理関連プロパティ（例: 質量、摩擦、反発係数）をカプセル化する新しいコンポーネントです。
    *   **`RenderComponent`** (既存): メッシュデータ、マテリアルプロパティ、シェーダー割り当てを効果的に管理できることを確認します。
    *   **`CollisionComponent`**: 衝突形状、タイプを定義し、衝突イベント関連データを格納する可能性のある新しいコンポーネントです。
    *   **`SoundComponent`**: サウンド再生トリガー、関連するオーディオアセット、サウンドプロパティを管理する新しいコンポーネントです。
    *   **`ScriptComponent`**: エンティティを Lua スクリプトやその他のスクリプティングロジックにリンクするための新しいコンポーネントです。

4.  **コアシステムの作成（未存在の場合）:**
    *   **`PhysicsSystem`**: Bullet Physics との統合、物理シミュレーションに基づく `PhysicsComponent` の更新、衝突の検出、衝突イベントのディスパッチを担当する新しいシステムです。
    *   **`SoundSystem`**: `SoundComponent` を処理し、オーディオエンジンを介してオーディオ再生をトリガーする新しいシステムです。
    *   **`ScriptSystem`**: `ScriptComponent` に関連付けられたスクリプトの実行、そのライフサイクルの管理、関連するエンティティデータの受け渡しを担当する新しいシステムです。

#### **フェーズ 2: 段階的な移行 - `GameObject` サブクラスを一つずつ移行**

このフェーズは反復的に実行されます。一つの `GameObject` サブクラスを選択し、その移行を実行し、次のサブクラスに進む前に変更を徹底的に検証します。単純で依存関係の少ないクラス（例: `StaticObject`、`Stone`）から始め、より複雑なクラス（例: `Player`）へと徐々に移行することをお勧めします。

各 `GameObject` サブクラス（例: `Stone`）について:

1.  **ゲーム固有のコンポーネントの作成:**
    *   `Stone` クラスが汎用コンポーネントではカバーされない固有のデータや状態を持つ場合、この情報を保持するための専用の `StoneComponent` を作成します。汎用コンポーネント（Transform、Physics、Render）のみで十分な場合は、新しいコンポーネントは不要です。

2.  **ゲーム固有のシステムの作成（必要な場合）:**
    *   `Stone` クラスが固有のロジック（例: 特定の `update()` 動作、カスタム衝突応答、AI）を含む場合、`StoneSystem` を作成します。このシステムは、`StoneComponent`（存在する場合）およびその他の関連コンポーネント（例: `TransformComponent`、`PhysicsComponent`）を操作して、特定のロジックを実装します。

3.  **`GameObject` サブクラスをエンティティファクトリにリファクタリング:**
    *   既存の `Stone` クラス（または新しい `StoneFactory` クラス）を、ECS エンティティを作成するためのファクトリとして機能するように変更します。これには以下が含まれます。
        *   `EntityManager::create_entity()` を呼び出して新しい `Entity` を取得します。
        *   この新しいエンティティにすべての必要なコンポーネント（例: `TransformComponent`、`PhysicsComponent`、`RenderComponent`、`StoneComponent`）を追加します。
        *   これらのコンポーネントを、以前 `Stone` オブジェクトが管理していたデータで初期化します。
    *   重要な点として、このクラスの `GameObject` からの継承を削除します。

4.  **インスタンス化箇所の更新:**
    *   `Stone` のインスタンスが作成されているすべてのコード箇所（例: `new Stone()`）を特定し、変更します。
    *   これらのインスタンス化の呼び出しを、ファクトリが提供する新しいエンティティ作成ロジック（例: `StoneFactory::createStoneEntity()`）に置き換えます。

5.  **相互作用箇所の更新:**
    *   `Stone` オブジェクトがアクセス、操作、またはクエリされているすべてのコードセクションを特定します。
    *   これらの直接的なオブジェクト相互作用を、ECS スタイルのクエリとコンポーネントアクセス（例: `EntityManager::get_component<TransformComponent>(stoneEntity)`）に置き換えます。
    *   衝突コールバック（例: `on_collide_with`）は、`PhysicsSystem` または専用の `CollisionSystem` 内で再実装する必要があります。これらのシステムは、`StoneSystem`（または他の関連システム）が購読して反応できるイベントをディスパッチします。

6.  **`GameObject` 固有コードの削除:**
    *   すべての `GameObject` サブクラスが ECS モデルに正常に移行されたら、`GameObject` クラス自体、および冗長になった関連マネージャークラス（例: `ActiveObjectManager`）をコードベースから削除する必要があります。

#### **フェーズ 3: シェーダーシステムの簡素化（並行または後続）**

1.  **シェーダーリフレクションの統合:**
    *   `memo.md` で示唆されている `D3DReflect` を調査し、シェーダーファイルを自動的に解析するために統合します。
    *   シェーダーリフレクションを利用して、定数バッファ、テクスチャ、入力レイアウトに関する包括的な情報をシェーダーコードから直接抽出します。
    *   この情報を活用して、コンパイル時に C++ 構造体/メタデータを生成するか、実行時にシェーダーリソースを動的にバインドすることで、手動でのパラメータ設定や各パラメータに対する `typeid().hash_code()` への依存を減らします。

2.  **柔軟なリソースバインディング:**
    *   `BaseShader` およびその派生クラスを修正し、異なるシェーダーステージ（頂点シェーダー、ピクセルシェーダー、ジオメトリシェーダーなど）間で定数バッファとテクスチャをより柔軟にバインドできるメカニズムをサポートします。これは厳密な 1:1 マッピングから脱却する必要があります。
    *   単一のシェーダープログラム内で複数の定数バッファとテクスチャの使用を可能にします。

3.  **RenderSystem との統合:**
    *   `RenderSystem` が、新しく簡素化された柔軟なシェーダーシステムを効率的に利用するように更新されていることを確認します。これには、コンポーネントデータ（例: `TransformComponent`、`RenderComponent`）を最適化された方法でシェーダーに渡すことが含まれます。

#### **フェーズ 4: クリーンアップと検証**

1.  **冗長なコードの削除:** 移行後に不要になったすべての `GameObject` 関連コード、マネージャークラス、ヘルパー関数、およびその他のコードを体系的に削除します。
2.  **ドキュメントの更新:** 新しい ECS アーキテクチャを反映するように、すべての関連プロジェクトドキュメント（設計原則、コンポーネント/システム定義、使用ガイドラインなど）を徹底的に更新します。
3.  **徹底的なテスト:** 既存のすべてのユニットテストと統合テストを実行します。新しく作成された ECS コンポーネントとシステムに対して、その正確性と安定性を確保するための新しいテストを開発し、実装します。
4.  **パフォーマンスプロファイリング:** アプリケーションの包括的なパフォーマンスプロファイリングを実施し、ECS 移行によってパフォーマンスの低下が発生していないことを確認します。理想的には、より良いキャッシュ局所性とデータ指向設計原則により、移行によってパフォーマンスが向上するはずです。
