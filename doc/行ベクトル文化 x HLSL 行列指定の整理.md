# 行ベクトル文化 × HLSL 行列指定の整理

〜「Transpose してるのに動かない」理由を検証で理解する〜

HLSL の `row_major / column_major`、
さらに「行ベクトルで計算するのか／列ベクトルで計算するのか」。

このあたりは **資料・書籍・サンプルごとに前提が違い**、
「結局どれを採用すればいいのか分からない」状態に陥りがちです。

そこで、実際に **4つのパターンを用意して動作検証** を行いました。

この記事では、

* 各パターンが **なぜ動いた／動かなかったのか**
* そこから見えてくる **本質的なルール**

を整理します。

---

## 検証した 4 パターン

### パターン A（従来の blue-sky / DirectX11 時代の本）

| 項目        | 内容                    |
| --------- | --------------------- |
| C++ 側     | 行ベクトル                 |
| Transpose | あり                    |
| HLSL 行列指定 | `column_major`（デフォルト） |
| HLSL 計算順序 | 行ベクトル                 |
| 結果        | **動く**                |

👉 いわゆる「**教科書的・伝統的構成**」。

* C++ では行ベクトル文化
* GPU に渡す前に転置
* HLSL 側では `mul(v, M)`

多くの DirectX11 本や古いサンプルがこの形です。

---

### パターン B（新しい blue-sky）

| 項目        | 内容          |
| --------- | ----------- |
| C++ 側     | 行ベクトル       |
| Transpose | なし          |
| HLSL 行列指定 | `row_major` |
| HLSL 計算順序 | 行ベクトル       |
| 結果        | **動く**      |

👉 **意図が一貫している構成**。

* C++ も HLSL も「行ベクトルで考える」
* 転置はしない
* メモリ配置だけを `row_major` で明示

「転置を前提にしない」という点で、
現代的・分かりやすい設計です。

---

### パターン C（テスト：動かない例）

| 項目        | 内容             |
| --------- | -------------- |
| C++ 側     | 行ベクトル          |
| Transpose | あり             |
| HLSL 行列指定 | `column_major` |
| HLSL 計算順序 | **列ベクトル**      |
| 結果        | **動かない**       |

ここが一番重要なケースです。

#### なぜ動かないのか？

* **転置済み**
* **column_major**
* **列ベクトル計算**

一見「正しそう」に見えますが、
実はここで **意味が二重に反転** しています。

* 転置で意味を反転
* 計算順序（列ベクトル）でさらに反転

結果として、
**数学的に想定している行列と別物を掛けている** 状態になります。

---

### パターン D（テスト・西田さん DirectX12 系）

| 項目        | 内容             |
| --------- | -------------- |
| C++ 側     | 行ベクトル          |
| Transpose | なし             |
| HLSL 行列指定 | `column_major` |
| HLSL 計算順序 | 列ベクトル          |
| 結果        | **動く**         |

👉 一見ややこしいが、**中身は一貫している**。

* C++ は行ベクトル
* 転置なし
* HLSL では「列ベクトル前提」で解釈

つまり、

> **CPU 側の行列を、そのまま「列ベクトル用の行列」として使っている**

という構図です。

DirectX12 系の資料や一部の実践的サンプルで見かける形です。

---

## 検証から分かった本質

今回の検証で分かったのは、次の一点です。

> **row_major / column_major は「文化」ではなく「メモリ配置」
> 行ベクトル / 列ベクトルは「計算の約束」**

そして、重要なのはこれ。

### ✅ 動く条件はただ一つ

> **「CPU 側で作った行列の“意味”と、
> HLSL 側で掛け算するときの“解釈”が一致していること」**

* 転置するかしないか
* row_major か column_major か
* 行ベクトルで書くか列ベクトルで書くか

これらは **手段** であって、目的ではありません。

---

## 4 パターンを一言で整理すると

| パターン | 評価               |
| ---- | ---------------- |
| A    | 歴史的経緯で成立した「お作法」  |
| B    | 意図が最も分かりやすい・おすすめ |
| C    | 意味がズレて破綻する典型例    |
| D    | 列ベクトル文化を素直に採用した形 |

---

## 個人的な結論

* **新規実装ならパターン B が一番事故らない**
* 「転置ありき」の設計は、理解コストが高い
* 「なぜ動いているか説明できない構成」は将来の地雷

行列が分からなくなる原因の多くは、

> 「メモリ配置」と「数学的な掛け算」を
> 無意識に混ぜてしまうこと

今回の検証は、それを切り分けて理解する良い材料になりました。
