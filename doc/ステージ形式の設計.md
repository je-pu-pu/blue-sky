2026-11-10 作成。利用者の決定 :「今の独自の .stage 形式を、ECS の部品とイベントをそのまま書けるデータ形式に移す」（Lua はいったん置いておく）。
パスは worktree からの相対。「（推測）」以外はコードとデータで確かめた。決めたことは 5 章に日付付きで書き足す。

### 1.3 イベント

- 動きの表は command_map_（setup_command、36 個）。引数は空白区切りの文字列。
- ステージの 122 個の event はすべて `turn-on`。条件はプレイヤーか石が速さ 0.5 以上で当たったこと。同じ物は 0.5 秒あけないと押せない。
- `timer 間隔 回数 コマンド…` は文字列のまま預け、時間が来たら解釈し直す（名前が見つからないと遊んでいる最中に例外）。
- exec と event で使っている動き : 空・BGM・BPM、影・紙・環境光の色（そのまま／少しずつ）、光の位置、線・紙・強調・陰影・風船の音の種類、音の読み込み・再生・停止、物体の作成・目標地点・向き・重力・質量・当たりの応答・ゆらぎ・アニメーション・状態（break・float・rotation・set_visible・turn-off）、ステージの終わり。

## 2. 新しい形式（TOML）

### 2.1 なぜ TOML か

ステージの入れ子は最も深くて 4 段、配列（物体 425・event 122・exec 111）は順番に意味がある（作った順が描く順・スイッチを押す順）。TOML は配列で順番を保て、コメントがあり（今 58 行使っている）、型がはっきりしている。toml++ はヘッダだけ・MIT で、値ごとに行番号を持つのでエラーに「ファイル:行」を出せる。JSON はコメントが無く手書きの量が多い。YAML は型を勝手に決め（`no` が false）、yaml-cpp のビルドが要る。

- toml++ の版は v3.4.0（TOML 1.0・C++17 以上）が設計担当の知る最新（要確認）。source/lib/include/toml++/toml.hpp に置き、`TOML_HEADER_ONLY 0` で実装を 1 つの .cpp に置く案。
- 表のキーの順は保たれない前提で、順番の要るものは配列に入れる（toml++ の表の順は要確認）。

### 2.2 書き方（ファイル名 `0-0.stage.toml`）

| 区画 | 中身 |
|---|---|
| `format = 1` | 形式の版 |
| `[stage]` | collision・ground・bgm（読み込むときに 1 回） |
| `[environment]` | bgm・bgm_loop・bpm・sky_box・各色・light_position・line_type・paper_type・drawing_accent_scale・shading_enabled・balloon_sound_type（やり直すたびに当て直す） |
| `[sounds]` | `fin = { file = "…", replace = true }`（読み込むときに 1 回） |
| `[player]` `[goal]` | position・camera_direction |
| `[[object]]` | type・name・position・direction（・size）、種類の決まりの上書き、`on_turn_on = [動き…]`・`on_turn_off` |
| `[[event]]` | `when = "start"`（やり直すたび）と `then = [動き…]`。後で `when = { goal = true }`・`{ time = 30 }` など |
| まとめ書き | `[[object]] type = "balloon" direction = 0 positions = [[x,y,z], …]`（名前もイベントも無い同じ種類が 3 つ以上続く所。順番は変えない） |

**動き**は `{ do = "名前", … }` の 1 行の表。どの動きにも `delay = 秒` か `every = 秒, count = 回数` を付けられる。

| 今 | 新しい書き方 |
|---|---|
| set_*・change_sky_box・change_bgm・change_bpm | `{ do = "set", shadow_color = [0,0,0,1] }`（キーは [environment] と同じ） |
| set_*_target | `{ do = "fade", shadow_color = [1,0,0,1], speed = 0.01 }` |
| play_sound など | `play_sound {sound, force, loop}`・`stop_sound`・`stop_all_sounds`・`load_sound {name, file, replace}` |
| game_object.create | `{ do = "spawn", model = "…", position = [...] }` |
| set_target_location / direction | `move_to {target, position, speed}`・`turn_to {target, direction or face, speed}` |
| set_mass・set_gravity など | `set_body {target, mass / gravity / angular_factor / kinematic / contact_response}` |
| ゆらぎ・アニメーション | `set_flicker`・`start_flickering`・`play_animation`・`set_animation_speed` |
| action | `switch {target, state = "on"/"off"/"broken"}`（イベントは起こさない）・`set_mode`・`set_visible`・`break_animation` |
| end_by_last_switch | `{ do = "end_stage" }` |

### 2.3 物体と ObjectFactory

- `type` を ObjectFactory の種類にする。ECS だけの種類（static・medal・goal・rocket・umbrella、段階 4 の残りが終われば ladder・stone・switch も）は、ObjectSpec の欄（mass・size・shape・hard・block・safe_footing・gravity・restart_mass・height_offset・model）を上書きできる。
- 位置・向きは作る前に spec に入れる（やり直したときに ECS の仕組みのまま元へ戻る）。ObjectFactory に `find_spec(種類)` と `create(const ObjectDesc&)` を足す。
- 部品を直接書く形（`components.SimpleObject = {…}`、種類を持たない `[[entity]]`）は後の段階。「部品の名前 → 欄を読む関数」の表（ComponentRegistry）が要る。
- 動きは読み込むときに `Action`（種類と型の付いた引数）へ変換する。DelayedCommand は文字列ではなく Action を持ち、遊んでいる最中に解釈し直さない。スイッチが ECS になったら `on_turn_on` は SwitchComponent（またはイベントの部品）へそのまま移す。

### 2.4 .obj・.png・.list・.intro・.outro

.obj・.png は今のまま。.list はステージと関係ないので触らない。.intro・.outro は 5 章の決定による。

## 5. 決めること

1. イベントの置き場所（推奨 : スイッチの中に `on_turn_on = [...]`、場所と関係ない条件は `[[event]] when = …`）
2. 古い形式を消す時期（推奨 : 16 個すべてを確かめたら段階 5 ですぐ消す。変換ツールは残す）
3. .intro・.outro（推奨 : 今回は移さず、別の作業で TOML にし `layer-rotate` の不具合も直す）

### 決定（2026-11-10、利用者）
1. イベントの置き場所 : スイッチの中に `on_turn_on = [...]` と書く。場所と関係ない条件（始まったとき・ゴールなど）は `[[event]] when = …` に書く
2. 古い形式 : 16 個すべてを 3.2 で確かめたら、段階 5 ですぐ消す。変換ツールは tools/ に残す
3. .intro・.outro : 今回は移さない。別の作業で TOML にし、`layer-rotate` の不具合もそのときに直す

後で決めること : 書いていない環境の値をやり直しで既定値に戻すか（今は戻らない）・`video.shadow-map-enabled 0`（効かせると画面が変わる）・0-2 の `[stage].bgm`（やり直しで鳴らし直さない）。

### 6.2 決めたこと

| # | 決めたこと | 理由 |
|---|---|---|
| 1 | 当てる順は BGM → 当たりの形 → 地面 → 物体（書いた順）→ プレイヤー → ゴール | 以前は書いた順で、プレイヤーの剛体を加える時点がステージごとに違った。TOML では [player] の場所に意味が無い。物体の作る順・名前・イベントの順（EntityId）は変わらない。ダンプ・確かめのログは変える前と同じだった |
| 2 | 動きの引数は「書いてある値だけ」を持ち、書いていない値は行う側（run_action）が以前と同じ既定の値を使う。ただし以前 0 のままだった 3 つの数（位置・重力など）は、1 つでも書いてあれば足りない所を 0 で補う。色は書いた成分だけ（1〜4 個）変える | 以前の stringstream の「読めなかった所から後は前の値のまま」を、型を付けたまま同じ結果にするため（0-3 の `set_ambient_color 0 0 0` は透明度を変えない） |
| 3 | 見つからない名前を指す動きは、古い読み方と変換ツールでは捨てて警告、TOML の読み方では残して警告（3.4） | 名前は読み込むときにしか付かないので、以前も遊んでいる最中に何もしなかった。捨てても動きは同じ |
| 4 | 「同梱の全ステージが警告 0」にする方法 : 変換ツールが捨てた物（どこも読まない行・余った数・name の 2 語目・無い名前を指す動き）を TOML の値に書かず、`# 変換で捨てた…` のコメントで残す | 捨てた物は TOML に入らないので、読んでも警告にならない。何を捨てたかはファイルのコメントと変換の報告に残る |
| 5 | 失敗の「その項目だけ飛ばす」の単位 : 知らないキーはそのキーだけ、型の違い・必須の欠け・組み合わせの誤りはその物体・動きを丸ごと、知らない種類・動きはその物体・動き | 型の違う引数のまま動きを行うと、書いた人の意図と違うことが起きるため |
| 6 | bgm.loop は `[stage] bgm_loop`、読み込むときの BPM は `[stage] bgm_bpm` に置いた（2.2 では bgm_loop は [environment]） | やり直しで当て直す値ではなく、BGM を鳴らすたびに読む設定のため。[environment] と [sounds] は今回は作っていない（変換は exec を 1 対 1 で `[[event]] when = "start"` に写すので使う所が無い。3.1） |
| 7 | 動かない物は `type = "static"`・`model`・`rotation`。向きは回転の x（以前の object 行と同じ）で、`direction` は書けない | 以前の object 行の 4 つ目の数が回転の x と向きの両方だった |
| 8 | 当たりの応答は `set_body { contact_response = false }`（以前の set_no_contact_response 1 の逆の値） | 2.2 の名前のとおり。変換ツールが逆にして写す |
| 9 | timer は回数 1 なら `delay = 秒`、ほかは `every = 秒, count = 回数` | 2.2 のとおり。どちらも Action の is_timed・interval・count になる |
| 10 | 数は読んだ結果では double で持ち、当てるときに float にする | 以前は文字列から直接 float に読んでいた。10 進の文字列 → double → float と 10 進 → float は、ちょうど中間の値でだけ 1 ulp 違い得る（同梱のステージでは比べた範囲で違いは出ていない） |

### 6.3 確かめた結果

すべて開発用の手段で、同じ版（段階 4、d12a97c6）で古い形式（BLUE_SKY_STAGE_FORMAT=legacy）と TOML を 16 個すべて起動して比べた（ステージごとに 4 通り × 2 = 128 回）。作業用の確かめのスクリプトは worktree の外（%TEMP%\stagefmt）に置いた。

| 確かめ | 結果 |
|---|---|
| 作った物体の一覧（BLUE_SKY_DEBUG_DUMP_STAGE） | 16 個すべてで同じ（番号・種類・位置・向き・名前・スイッチのイベントの数）。段階 5 の版（古い形式を消した後）でも 16 個すべて同じ |
| スイッチを押す（BLUE_SKY_DEBUG_PRESS_SWITCHES。入った・目標地点へ動かします・着きました） | 16 個すべてで同じ。0-1 2・1・0、0-3 2・0・0、1-0 1・0・0、1-1 2・3・2、1-2 1・1・1、1-3 2・0・0、2-0 1・1・1、2-1 13・39・38、2-2 2・0・0、ext-1 1・1・1（ほかはスイッチ無し）。手順の基準の値（1-1・2-1・1-2・0-1・2-0）とも同じ |
| 物体巡り（BLUE_SKY_DEBUG_VISIT_OBJECTS） | 16 個すべてで結果が同じ |
| 石投げ（BLUE_SKY_DEBUG_THROW_STONES） | 15 個で同じ。1-2 のスイッチだけ 切 → 入（移す前の同じ版でも起動ごとに入・切が変わる所。ECS 移行計画の段階 4 の記録と同じ） |
| 画面（60・120 フレーム目） | 動かない場面（0-1・1-1・1-2・2-0・2-1・ext-0・ext-1・ext-2 など）は差の平均 0.1 以下。差の大きい所（0-0・0-2・1-0・1-3・2-2・staff。最大で平均 28）は、時間で変わる紙の模様と、落ちる途中・置き直した直後の位置の差。同じ版を 2 回動かしても同じ程度に変わる（段階 1 で 1-0・1-3・staff を 2 回動かして確かめた。1-3 の 60 フレーム目は同じ版どうしで 75%） |

段階 1・2 は、それぞれ変える前（53bd888b）と、ダンプ（16 個）・スイッチ（1-1・2-1・1-2・0-1・2-0）・物体巡り（0-1・2-0・0-0・1-0・1-3・0-2）・石投げ（1-0・1-1・1-2・2-0・2-1）で比べて同じだった（揺れる所のほか。段階 2 の 2-1 の switch-m のイベントが 33 → 32 になったのは捨てた switch-j の分）。石投げの 2-1 で拾う石が 7 個になったことが 1 回あり、同じ版でもう 2 回動かすと 8 個だった（物理の揺れ）。

ステージ選びは、ストーリーの 1 ページ目とおまけのページ（ext-0〜2・staff の 4 個）に .stage.toml のステージが並ぶことを画面で確かめた。
