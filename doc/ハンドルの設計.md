# ハンドルの設計（Handle と WeakHandle）

2026-11-11、利用者と検討して決めた。今のハンドル（`core::ResourceHandle`：二度と使わない 64 ビットの番号。引くたびに `std::unordered_map` を 1 回引く）を作り替える。
経緯 : 生ポインタをハンドルにした（doc/ECS移行計画.md の 4 章・4.1、設計上の問題 D4）結果、使うたびに表を引く手間が増えた。1 万を超える Entity の前提では効いてくる（推測で 1 フレーム 1〜3 ms）ので、安全さを保ったまま速くする。

## 1. 決めたこと

- **持ち主の印 `Handle` は ResourceManager だけが持つ。** 作るのも解放するのも ResourceManager だけ（ほかは型の上で作れない・解放できない。コピーできず、ムーブだけ）。
- **ほかの所は `WeakHandle` を持つ。** WeakHandle は Handle へのポインタだけを持つ（8 バイト）。ビットの割り当て（管理側の番号・スロット番号・世代を 64 ビットに詰める案）はしない。
- **Handle は実際のリソースへのポインタを持つ。** リソースを解放すると、Handle の中のポインタを nullptr にする。**Handle 自体は解放しない**（場所も動かさない）。
- **WeakHandle は Handle をたどって、無効になったことを知る**（`get()` が nullptr）。weak_ptr の `lock()`・`expired()` と同じ使い方。shared_ptr は使わない（持ち主がはっきりしなくなる・引くたびに数の増減がある）。
- **差し替え（読み直し）は、同じ Handle の中のポインタを替えるだけ。** 持っている WeakHandle は、そのまま新しい中身を引く。
- **一度解放した名前をもう一度読んだときは、同じ Handle を使い回す**（名前でリソースを指す今の使い方に合い、Handle も増えない。古い WeakHandle は再び引けるようになる）。

```cpp
template< typename T >
class Handle                 // ResourceManager の置き場にだけある。作ったら動かさない・解放しない
{
    friend class ResourceManager< T >;
    T* resource_ = nullptr;  // 実際のリソース。解放したら nullptr
};

template< typename T >
class WeakHandle             // 8 バイト。誰でも持てる・コピーできる
{
    const Handle< T >* handle_ = nullptr;
public:
    T*   get() const     { return handle_ ? handle_->resource_ : nullptr; }   // weak_ptr::lock に当たる
    bool expired() const { return get() == nullptr; }
};
```

## 2. 守ること（問題点と対策）

| 問題 | 対策 |
|---|---|
| Handle の分のメモリが戻らない（解放しても 8 バイトが残る） | 名前で読むリソースは同じ Handle を使い回す。物体ごとの複製（make_model_unique など）の使い捨てのリソースだけが増える。Handle の数をデバッグ表示に出して増え方を見えるようにする。増えすぎたら、その種類だけ別の形（添字＋世代）にする逃げ道を残す |
| Handle の場所が動くと WeakHandle が壊れる | Handle はページ（決まった大きさのかたまり）に置き、伸ばすときはページを足すだけ（既存のページは動かさない・捨てない）。ECS の `core/ecs/StablePool.h` と同じ考え方 |
| Handle の置き場が先に壊れると WeakHandle が壊れる | ResourceManager（GraphicsManager・SoundManager が持つ）はアプリの間ずっと生きている決まり。WeakHandle を static・グローバルに置かない |
| 別のスレッドから書き換える | 表と Handle を書き換えるのはメインスレッドだけ（別のスレッドで読んだ物はメインスレッドに渡して登録する。今の AsyncLoader と同じ）。ロックも atomic も要らない |
| フレームの途中でリソースが消える | 解放と差し替えはフレームの終わり（Present の後）とシーンの切り替えにまとめる。1 フレームの中では、引いたポインタを使い回してよい（次のフレームへ持ち越さない。Debug ビルドで持ち越しを検出する） |
| メモリ上の並び | Handle は 8 バイトのまま保つ（デバッグ用の名前などは別の表に置く）。使い捨てのリソースの Handle は別のページにまとめ、名前付きの Handle の密度を保つ。描く流れは 1 フレームに 1 回だけ引いてポインタの配列にする |
| ファイルに保存できない | 保存するときは名前で書く（どの形でも同じ） |

## 3. 引く手間の見積もり（推測。作り替えの前後で測る）

| 形 | 引くときにすること | 1 回の目安（Release） |
|---|---|---|
| 以前（生ポインタ） | ポインタを 1 回たどる | 約 1 ns |
| 今（番号＋ハッシュの表） | ハッシュを計算して表を探す | 約 10〜30 ns |
| この設計 | WeakHandle → Handle → リソースとたどる | 約 1〜2 ns |

## 4. 進め方

1. 計測を足す : ハンドルを引く手間のベンチマーク（1 万・10 万個。生ポインタ・今の形・この設計）と、本編のステージのフレームの時間。今の作りの数字を残す
2. 解放と差し替えをフレームの終わりにまとめる（Debug で持ち越しを検出）
3. Handle（ResourceManager だけ）と WeakHandle を作り、ResourceManager の中を作り替える。使う側は `resolve_*( handle )` を `handle.get()` にする
4. 描く流れでは 1 フレームに 1 回だけ引く
5. もう一度測って比べる

シーンを片付けた後に debug_log に出す（「中身のある数/作った数」）。シーンを順に替える確かめ（title → stage_select → game_play 1-1 → title → stage_select → game_play 2-0 → ending → title → story_text 1-1 → stage_select → game_play 1-1）の終わりで、

- 音はシーンごとに外して読み直すが、同じ名前は同じ Handle を使うので、ほとんど増えない（中身のあるのは 3）
- モデル・メッシュ・テクスチャ・シェーダーは、今はシーンをまたいで残す（キャッシュ）ので、解放した Handle は無い。シェーダーは game_play 2-0 を読んだ後は増えない（55 → 98 → 98）
- Handle の置き場は 1 種類あたり 2 KB のページが 1 枚（シェーダーは 98 個で 1 枚）

### 5.4 決めたこと

- **Handle はムーブもできなくした**（1 章は「ムーブだけ」）。作ったら動かさない決まりなので、ムーブも要らない。置き場のページは `new Handle[ 256 ]` で作る（コンストラクタは ResourceManager にだけ見えるので、ほかでは作れない）
- **`ResourceHandle` を WeakHandle の別名にした**。ModelHandle・TextureHandle・ShaderHandle・SoundHandle をそのまま使える。`ResourceManager::Handle`（以前の番号のハンドルの別名）は `WeakHandle` に名前を変えた（Handle は持ち主の印の名前なので）
- **`resolve_*` の関数は残した**（中身は `get()`）。ResourceResolver の窓口（doc/描画の窓口の分割.md）と偽物のテストが使っている。表を引かないので、残しても遅くならない
- **同じ名前で読み直すと同じ Handle**。ただし、名前を 2 つ持っていたリソースを手放した後、片方の名前で読み直して Handle を使っていたら、もう片方の名前は新しい Handle にする（同じ Handle が別々のリソースを指すことになるため）
- **名前の無いリソースの Handle は使い回さない**（古い WeakHandle が別のものを指さないように）。clone_model などは作るたびに Handle が増える
- **解放待ちのハンドルへの replace は失敗にする**（以前の「解放済みのハンドルへの replace は失敗」と同じ）。別の ResourceManager のハンドルでの replace も失敗にする
- **差し替えは、すぐに新しい中身を指す**（古い中身はフレームの終わりまで生きる）。解放は、フレームの終わりまで同じハンドルで古い中身を引ける
- **フレームの途中で入った描く対象は、入るときには引かない**。部品が揃った後でハンドルを設定する作り（ObjectFactory など）があるので、次の `resolve_models` で全部を引き直す（めったに無いので、全部でよい）
- **Debug での持ち越しの検出は、描く対象のモデルだけ**。フレームの終わりに `RenderTarget::model` を nullptr に戻す。生ポインタ一般の持ち越しは、ポインタを追う仕組みが無いので検出しない
- **使い捨てのリソースの Handle を別のページにまとめる、は行わなかった**。Handle は add のとき（名前を付ける前）に作るので、名前が付くかどうかが分からない。名前付きの Handle の数が少ない（多くて 100 個前後）ので、密度の差は小さい
- **GraphicsManager::flush_releases の順**はモデル → メッシュ → シェーダー → テクスチャ → スキニング（使う側を先に）

### 5.6 残り

- 1 万を超える Entity でのフレームの時間（本編のステージの物体は数十個なので、計算での見積もりだけ）
- Model が持つシェーダーの一覧（`std::vector< Shader* >`）・`GraphicsManager::shadow_map_shader_` は生ポインタのまま（doc/ECS移行計画.md の 4.1 の残り）。解放をフレームの終わりにまとめたので、フレームの中では壊れない
- Handle の数が増えすぎたときの逃げ道（その種類だけ添字＋世代にする）は、今は要らない（増えるのは名前の無いリソースだけで、数十個）
